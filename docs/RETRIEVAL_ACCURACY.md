# 검색·답변 정확도 — 측정과 개선 기록

"답변 정확도가 너무 떨어진다" 는 실사용 보고에서 출발해, 원인을 찾고 고치고
검증한 과정을 기록한다. 각 결정에는 근거가 된 실측치를 함께 남긴다.

두 가지를 특히 분명히 적는다.

- **채택하지 않은 변경**. 왜 안 했는지가 왜 했는지만큼 중요하다. 이 작업에서
  내가 만든 개선안 중 여럿이 측정에서 졌다.
- **측정으로 구분되지 않는 차이**. 비율만 보면 개선처럼 보이지만 잡음인 경우가
  많았다. 아래에서 그 구분을 명시한다.

---

## 1. 왜 이전 측정은 결함을 못 잡았나

개선에 앞서 평가부터 다시 만들었다. 이전 평가셋이 결함을 감추고 있었기 때문이다.

이전 평가셋은 손으로 쓴 22~28문항이었고, 정답 키가 질문에 그대로 들어 있었다:

```
Q. NatWest 사례는 어떤 내용인가요?          -> 정답 chunk 에 "NatWest" 가 있음
Q. Bitbucket EOS 대응 사례를 알려주세요      -> 정답 chunk 에 "Bitbucket EOS" 가 있음
```

이런 질문은 BM25(키워드 검색)가 항상 적중한다. recall@7 = 100% 가 나왔지만
실제 사용자 질문은 실패했다:

```
Q. DAP에서 쓸 수 있는 가장 큰 자체 호스팅 모델은 뭔가요?
   -> "관련 사내 문서를 찾을 수 없습니다."
```

문서에는 `Self-Managed환경 (폐쇄망)` 이라고 적혀 있다. 사용자는 "자체 호스팅"
이라고 물었다. **겹치는 단어가 하나도 없다.**

평가셋이 쉬웠던 것이 문제의 핵심이었다. 측정이 통과시키는 결함은 고쳐지지 않는다.

---

## 2. 측정 방법

### 2.1 평가셋 — 283문항, 두 유형 분리

코퍼스(142 chunk)를 chunk 단위로 읽어 질문·정답 쌍을 생성하고 두 유형으로
분리 태깅했다.

| 유형 | 문항 | 정의 |
|---|---|---|
| `direct` | 175 | 코퍼스 어휘를 그대로 써서 묻는다 |
| `gap` | 108 | 같은 사실을 **다른 표현**으로 묻는다 |

`gap` 문항에는 코퍼스의 고유명사를 넣지 못하게 했다. 그 고유명사가 바로
**정답**이어야 한다.

```
Self-Managed  ->  자체 호스팅 / 폐쇄망 / 인터넷 없이
GPU, VRAM     ->  그래픽카드 / 메모리 요구사항
credit        ->  요금 / 비용
```

유형을 분리해 보고하는 이유는, 하나의 숫자로 합치면 `gap` 쪽 결함이 `direct`
쪽 점수에 묻히기 때문이다. 실제로 그렇게 묻혀 있었다.

### 2.2 채점 — 키워드 매칭을 버린 이유

키워드 매칭은 이 작업 중 두 번 틀린 판정을 냈다. 정답을 오답으로 셌고, 반대도
가능했다. 정답 문장을 함께 주고 LLM 이 4분류로 판정한다.

| 판정 | 의미 |
|---|---|
| `correct` | 정답의 핵심 사실을 진술 (표현 차이 허용, 수치·고유명사는 일치 필요) |
| `partial` | 관련은 있으나 핵심이 빠지거나 불완전 |
| `wrong` | 다른 사실을 진술하거나 모순 |
| `refused` | "찾을 수 없습니다" 로 거절 |

`refused` 와 `wrong` 을 구분하는 것이 중요하다. **거절은 안전한 실패이고
오답은 위험한 실패다.** 하나로 합치면 이 차이가 사라진다.

### 2.3 차이가 진짜인지 판정하는 방법 — 짝 검정

이것이 이 작업에서 가장 중요한 방법론적 교정이다.

처음에는 설정별 정답률만 비교했다. 120문항에서 2문항 차이는 1.6%p 이고, 비율만
보면 개선처럼 보인다. 그러나 LLM 은 같은 입력에도 다른 출력을 낼 수 있어
**실행 간 편차만으로도 그 정도는 흔들린다.**

같은 문항에 대해 두 설정이 **서로 다르게 판정한 문항만** 세고(McNemar), 정확
이항 검정으로 p 값을 구한다. 둘 다 맞거나 둘 다 틀린 문항은 정보가 없다.

이 검정을 적용하자 내가 "개선" 이라고 부르려던 것들이 대부분 구분되지 않는
차이로 판명됐다. 아래 표에서 `구분 안 됨` 으로 표기된 항목이 그것이다.

### 2.4 실패 원인 분리

오답이 나왔을 때 그것이 검색 실패인지 생성 실패인지 구분해야 다음 작업 대상이
정해진다. 정답 chunk 가 실제 컨텍스트에 들어갔는지, 몇 번째였는지를 매 문항
기록한다.

### 2.5 측정 비용을 줄인 구조

**검색 실험**: 벡터 랭킹과 BM25 랭킹은 융합 파라미터와 무관하다. 질문당 한 번씩
전체 142 chunk 에 대한 두 랭킹을 뽑아 두면 이후 모든 융합 실험은 순수 파이썬
계산으로 끝난다. 임베딩 호출이 설정마다 283회씩 발생하는 대신 전체 283회로
고정된다. 검색 랭킹 계산에는 LLM 이 없으므로 이 측정은 **결정적**이다.

**답변 실험**: `RETRIEVAL_FINAL_K` 등은 모듈 임포트 시점 상수라 환경변수만으로는
못 바꾼다. 컨테이너 안에서 그래프를 직접 호출하고 모듈 전역을 런타임에 교체한다.
변수 하나만 정확히 바뀌고 HTTP 왕복도 없다. 입력 dict 는 `main.py` 의 `/chat` 과
동일하게 구성한다 — 운영 경로와 다른 입력으로 재면 측정이 무의미하다. 채택
설정은 별도로 실제 HTTP 경로에서 재검증한다.

## 3. 검색 단계

### 3.1 RRF 융합이 벡터 검색의 정답을 버리고 있었다

사용자 실패 질의를 추적한 결과:

```
질의 "DAP에서 쓸 수 있는 가장 큰 자체 호스팅 모델은?"
  벡터(Chroma) 단독 순위 :  9위    <- 찾았다
  BM25 단독 순위         : 미포함   <- 어휘가 안 겹쳐 실패
  RRF 융합 후            : 상위 20 밖  <- 버려졌다
```

원인은 RRF 상수 `k=60` 이다. 원 논문의 60 은 다수 시스템을 융합하는 TREC 환경
기준이다. 여기는 벡터와 BM25 둘뿐이고 **한쪽이 통째로 실패할 수 있다.**

k 가 크면 역순위 분포가 평평해져 "양쪽에 등장했는가" 가 "얼마나 잘 맞는가" 를
압도한다:

```
벡터  9위 + BM25 없음   =  1/69         = 0.0145
벡터 40위 + BM25 40위   =  1/100 x 2    = 0.0200   <- 이쪽이 이긴다
```

**정답 chunk 회수율 (283문항, 결정적 측정)**

| 설정 | 전체 r@20 | direct | gap | 전체 r@5 | gap r@5 |
|---|---|---|---|---|---|
| 벡터 단독 | 98.6% | 99.4% | 97.2% | 90.8% | — |
| BM25 단독 | 92.6% | 98.9% | **82.4%** | 85.9% | — |
| RRF k=60 (기존) | 98.2% | 100% | 95.4% | 91.5% | 83.3% |
| RRF k=30 | 98.6% | 100% | 96.3% | 92.2% | — |
| RRF k=15 | 99.3% | 100% | 98.1% | 92.9% | — |
| **RRF k=10 (채택)** | **99.6%** | **100%** | **99.1%** | **94.7%** | **89.8%** |
| RRF k=5 | 99.3% | 100% | 98.1% | 92.9% | — |
| RRF k=2 | 99.3% | 100% | 98.1% | 93.3% | — |

**짝 검정 (k=60 → k=10)**

| 지표 | 변화 | 불일치 (k=60만 / k=10만) | p | 판정 |
|---|---|---|---|---|
| recall@5 전체 | 91.5% → 94.7% | 1 / 10 | **0.012** | **유의** |
| recall@5 gap | 83.3% → 89.8% | 1 / 8 | **0.039** | **유의** |
| recall@20 전체 | 98.2% → 99.6% | 0 / 4 | 0.125 | 경향 |
| recall@20 gap | 95.4% → 99.1% | 0 / 4 | 0.125 | 경향 |

효과는 `recall@20` 이 아니라 **`recall@5` 에서 유의하다.** k=10 은 k=60 이
맞히던 문항을 사실상 잃지 않으면서(역방향 불일치 0~1건) 정답을 상위권으로
끌어올린다.

가장 중요한 관찰은 이것이다: **k=60 에서 융합 결과(gap 95.4%)가 벡터 단독
(97.2%)보다 나빴다.** 융합이 정보를 더한 게 아니라 깎고 있었다.

BM25 단독의 gap 82.4% 가 원인을 그대로 보여준다. 한국어 질의와 영문 표가 섞인
코퍼스에서 키워드 검색은 구조적으로 실패한다.
(BM25 단독 → RRF k=10, gap 불일치 0 대 18, p<0.001 — 융합 자체는 확실히 필요하다.)

> **작은 평가셋에 속았던 기록**: 28문항으로 먼저 스윕했을 때는 k=5 가 최적으로
> 나왔다(100%). 283문항에서는 k=10 이 낫다. 28문항에서의 순위 차이는 잡음이었다.

### 3.2 채택하지 않은 융합 대안

진단이 "한쪽 검색기가 통째로 실패한다" 였으므로 "두 랭킹 중 좋은 쪽만 취하기"
(min-rank)가 맞을 것 같았다. 측정에서 졌다.

| 전략 | 전체 r@20 | gap r@20 | 판정 |
|---|---|---|---|
| RRF k=10 | 99.6% | 99.1% | 채택 |
| min-rank | 98.9% | 97.2% | 기각 (역방향 불일치 2 대 0) |
| RRF 가중치 벡터 2배 | 98.6% | 96.3% | 기각 |
| RRF 가중치 BM25 2배 | 98.6% | 96.3% | 기각 |

**합의 신호를 완전히 버리면 손해다.** 적당한 k 의 RRF 가 두 신호를 모두 쓰면서
한쪽 실패에도 견딘다. fetch 창 크기는 80과 142가 차이 없어 기존 80을 유지했다.

### 3.3 co-retrieval 이 한 번도 작동한 적이 없었다

`expand_with_same_page` 는 형제 chunk(같은 페이지의 표 등)를 함께 가져오는
기능인데, 결과 리스트 **맨 뒤에 append** 했다. 호출 순서는 이렇다:

```
pool -> 상위 CANDIDATE_TOP_K(20)
     -> expand_with_same_page   (뒤에 append, 35개가 됨)
     -> boost_by_query_context  (인자 없이 호출돼 즉시 return — 무동작)
     -> docs[:RETRIEVAL_FINAL_K]  (=20)
```

`CANDIDATE_TOP_K` 와 `FINAL_K` 가 모두 20이므로 **append 된 형제는 전부 잘렸다.**
의도했던 "본문과 표를 함께 보기" 는 한 번도 작동하지 않았고, 그러면서 페이지당
Chroma 조회 2회는 계속 발생해 지연만 늘고 있었다.

(`boost_by_query_context` 는 `query_doc_topic` 인자가 있어야 동작하는데 호출부가
넘기지 않는다. 질의 쪽 topic 을 계산하는 코드가 어디에도 없다 — 미완성 기능이다.)

의도대로 작동하도록 고쳤다(`inline`: 형제를 부모 바로 뒤에 삽입, score 는 부모
점수 × 0.9). **정확도가 올라가지 않았다.**

| 설정 | 전체 | direct | gap | 대조군 대비 짝 검정 |
|---|---|---|---|---|
| `append` (기존, 무동작) | 90.0% | 91.9% | 87.0% | — |
| `off` (채택) | 89.2% | 89.2% | 89.1% | p=1.000 구분 안 됨 |
| `inline` (고친 버전) | 88.3% | 90.5% | 84.8% | p=1.000 구분 안 됨 |

세 모드는 **측정으로 구분되지 않는다.** 그러므로 "inline 이 나쁘다" 고 말할 수
없고, "형제를 끌어오는 것이 도움이 된다" 고도 말할 수 없다.

`off` 를 기본값으로 정한 근거는 정확도가 아니라 **비용**이다. `append` 는
가져온 형제가 FINAL_K 컷에서 전부 잘리는 것이 증명된 동작이면서 페이지당 Chroma
조회 2회는 계속 발생시킨다. 정확도가 같다면 하지 않는 편이 맞다.

`inline` 구현은 코드에 남겼다. 청킹 방식이 바뀌어 chunk 가 자체 완결적이지
않게 되면 재검토할 값이 있다. 현재는 청킹 단계에서 맥락 헤더와 표 행 단위
분할을 적용해 chunk 가 자체 완결적이라, 형제를 끌어올 이득이 적은 것으로 보인다.

### 3.4 컨텍스트 크기 — 최적점은 20 근처

| FINAL_K | 전체 | direct | gap | 거절 | 평균 응답 |
|---|---|---|---|---|---|
| 7 | 84.2% | 90.5% | 73.9% | 6.7% | 15.3s |
| 12 | 84.2% | 89.2% | 76.1% | 5.0% | 15.9s |
| **20 (채택)** | **90.0%** | **91.9%** | **87.0%** | **1.7%** | 16.5s |
| 30 | 87.5% | 90.5% | 82.6% | 1.7% | — |

**짝 검정 (K=7 → K=20)**: 전체 불일치 3 대 10, p=0.092 / gap 불일치 2 대 8,
p=0.109. 유의수준에는 못 미치지만 방향이 뚜렷하고, **답변 단계 실험 중 유일하게
신호가 있는 항목**이다. K=20 → K=30 은 p=0.727 로 구분되지 않는다.

컨텍스트가 길어지면 모델이 정답을 놓칠 거라 예상했으나 20까지는 반대였다.
recall@7 (97.5%) 과 recall@20 (99.6%) 의 차이는 2%p 뿐인데 답변 정확도는
5.8%p 차이가 났다 — 정답 chunk 를 담는 것 외에 **주변 chunk 가 답변을 돕는다.**

## 4. 라우팅 단계 — 검색을 건너뛰던 두 경로

이 절의 두 결함은 통계가 아니라 **재현으로 확인**된다. 특정 질의가 검색을
건너뛰었고, 수정 후 건너뛰지 않는다.

### 4.1 라우터가 검색 전에 "범위 밖" 을 추측했다

```
질의 "그래픽카드 요구사항이 어떻게 되나요?"
  실행 A -> router:rejected (1.2초, 검색 0회) -> "지원 범위에 포함되지 않습니다"
  실행 B -> GPU 요구사항 표로 정확히 답변 (15.4초)
```

같은 질문인데 비결정적이었고, 문서에 답이 있는데도 거절했다.

라우터 프롬프트는 `rejected` 를 **선택지로 제시조차 하지 않는데** `valid` 집합이
이를 받아주고 있었다. LLM 이 프롬프트에 없는 값을 만들어 그대로 통과했다.

근본 문제는 **라우터가 지식베이스 내용을 모른다**는 것이다. 색인된 문서를 본 적
없는 노드가 검색 전에 범위를 판정하는 것은 추측이며, 도메인 어휘(GPU/VRAM/크레딧)
가 일반 용어와 겹치는 이 코퍼스에서는 반드시 오판한다.

범위 판정을 검색 이후로 옮겼다. 관련 chunk 가 없으면 generator 가 "관련 사내
문서를 찾을 수 없습니다" 로 답한다 — 같은 거절이되 증거 기반이다. 보안 차단
(`security_gate`)은 패턴 판정이므로 그대로 유지한다.

**검증**: 같은 질문 5회 반복 → 5/5 정상 답변. 비결정성 해소.

### 4.2 `ai_guide` 오분류

```
질의 "CI/CD 빌드가 실패했을 때 로그를 일일이 정리하지 않고 원인을 빠르게
      찾으려면 어떤 기능을 쓰나요?"
  -> ai_guide -> 어시스턴트 기능 목록을 출력
  정답: 깃랩 듀오의 실패 원인 분석(Root Cause Analysis)
```

게이트가 트리거를 **부분 문자열**로만 검사해서, `"어떤 기능"` 이 들어 있으면
제품 기능을 묻는 문서 질의도 걸렸다. 사내 질의 중 흔한 형태다.

처음에는 길이 기준("짧으면 메타 질의")으로 고치려 했으나 실패했다:
`"보안 스캔 자동화에는 어떤 기능을 쓸 수 있나요?"` (27자)가 여전히 통과했다.
**길이는 내용의 유무를 나타내지 않는다.**

트리거 문구를 **제거한 나머지에 내용어가 남는지**로 판정하도록 바꿨다. 순수
메타 질의는 트리거를 빼면 조사·서술어만 남는다.

```
"어떤 기능이 있어?"        - "어떤 기능" = "이있어"    (3자)  -> ai_guide
"보안 스캔 자동화에는 ..."  - "어떤 기능" = "보안스캔..."       -> 검색
```

**검증**: 메타 8건 + 도메인 5건, 13/13 판정 일치.

### 4.3 범위 통제를 옮긴 뒤의 누출과 보완

4.1 에서 라우터의 사전 거절을 없애자 사내 무관 질의가 `no_retrieval` 로 분류되어
검색 없이 모델의 일반 지식이 그대로 나갔다:

```
"점심 메뉴 추천해줘" -> "오늘같이 날씨가 애매한 날엔 국물 요리(김치찌개...)"
```

`no_retrieval_answer` 노드는 검색을 거치지 않으므로 유일한 누출 경로다. 여기서
인사·기능안내 외 모든 질문을 거절하게 했다. 라우터의 사전 추측과 달리 이 판정은
"검색이 필요 없다고 이미 판정된 질의" 만 대상으로 하므로, 문서에 답이 있는
질문을 잘못 거절할 위험이 없다.

**검증**: 범위 밖 4건 전부 거절, 정상 질의 4건 전부 답변, 인젝션 2건 0.8초 차단.

## 5. 생성 단계

### 5.1 실패의 88% 는 검색이 아니라 생성에서 난다

283문항 실행의 오답 24건을 원인별로 나누면:

```
검색 실패 (정답 chunk 가 컨텍스트에 없음)    3건 (12%)
생성 실패 (컨텍스트에 있는데 답이 틀림)     21건 (88%)
```

검색 recall@20 이 99.6% 이므로 당연한 결과다. **이 시점부터 검색을 더 손대는
것은 의미가 없다.** 이 진단이 이후 작업 대상을 생성 단계로 옮긴 근거다.

`question_type` 별로 보면 약점이 한 곳에 몰려 있다:

| question_type | n | 정확도 |
|---|---|---|
| comparison | 5 | 100.0% |
| reasoning | 82 | 96.3% |
| exact_phrase | 84 | 94.0% |
| numerical | 71 | 90.1% |
| **list_n** | **41** | **78.0%** |

### 5.2 답변 규칙 2 가 필요한 정보까지 잘라내고 있었다

프롬프트 규칙은 "결과물의 성질" 로만 쓴다. 절차 지시("반드시 검증하라" 등)는
신형 모델이 답변에 그대로 출력하는 사고가 이미 있었다 (`generator.py` 주석 참조).

기존 규칙 2 는 "질문이 묻는 것만 답한다. 배경 설명·추가 정보는 넣지 않는다"
였다. 장황한 답변을 막으려는 의도였는데 수치를 해석하는 데 필요한 기준까지
잘라냈다:

```
Q. 파이프라인 실패 자동 수정으로 건당 얼마나 절약?
   전: "1.5시간 이상 절감"          정답: "시간당 $75 기준 약 1.5시간"
Q. 정보보호 통제 이행 여부를 얼마나 자주 점검?
   전: "반기 1회"                   정답: "반기 1회 ... 사내 정보보호위원회에 보고"
```

규칙을 "답을 해석하는 데 필요한 조건·단위·기준·전제는 함께 밝힌다" 로 완화했다.

**283문항 짝 비교 (판정 분포)**

| | correct | partial | wrong | refused |
|---|---|---|---|---|
| 기존 규칙 | 259 (91.5%) | 11 | **10** | 3 |
| 완화 규칙 | 264 (93.3%) | 10 | **6** | 3 |

**층위별 짝 검정**

| 층위 | 변화 | 불일치 (기존만 / 완화만) | p |
|---|---|---|---|
| 전체 | 91.5% → 93.3% | 4 / 9 | 0.267 |
| direct | 93.1% → 94.3% | 2 / 4 | 0.688 |
| gap | 88.9% → 91.7% | 2 / 5 | 0.453 |
| list_n | 78.0% → 85.4% | 0 / 3 | 0.250 |
| exact_phrase | 94.0% → 96.4% | 1 / 3 | 0.625 |
| reasoning | 96.3% → 95.1% | 1 / 0 | 1.000 |

**정답률 차이는 통계적으로 유의하지 않다** (p=0.267). 그럼에도 채택한 근거는
두 가지다.

1. **위험한 실패인 `wrong` 이 10 → 6 으로 줄었다.** 다른 사실을 단정하는 실패는
   지식 어시스턴트에서 가장 문제되는 유형이다. 거절이나 불완전한 답과 성격이
   다르다.
2. **퇴행이 없다.** 잃은 4건은 전부 `partial` 이고 `wrong` 으로 떨어진 건은
   없다. `list_n` 은 불일치 0 대 3 — 잃은 문항 없이 3건을 얻었다.

"정확도가 향상됐다" 고 단정할 근거는 아니다. 방향이 일관되고 손해가 없어서
택했다. 이 구분을 흐리지 않기 위해 여기 적어 둔다.

### 5.3 채택하지 않은 것 — 표 레이블 확인 규칙

"도입률 10%일 때 월 비용 절감액" 질문에 다른 조건의 표 행을 답한 사례가 있었다.
컨텍스트에 도입률별 유사 표가 여러 개 들어가면서 발생한다. 대응 규칙("질문이
지정한 행·열 레이블이 그 표에 실제로 있는지 확인한다")을 넣어 측정했다.

| 규칙 | 전체 | gap | 짝 검정 |
|---|---|---|---|
| (없음) | 89.2% | 89.1% | — |
| 표 레이블 확인 | 87.5% | 84.8% | 불일치 2 대 0, p=0.500 |

개선이 없었다(오히려 잃기만 했다). 규칙을 늘리면 모델이 과하게 조심스러워져
유효한 표까지 쓰지 않는 것으로 보인다. **기각.**

## 7. 남은 한계

- **표 오독**. 컨텍스트에 조건만 다른 유사 표가 여러 개 들어갈 때 발생한다.
  프롬프트 규칙으로는 해결되지 않았다(5.3). chunk 메타데이터에 표의 조건을
  명시하는 쪽이 맞아 보이나 검증하지 않았다.
- **검정력**. 283문항에서 답변 단계의 2~5문항 차이는 구분되지 않는다. 더 작은
  개선을 판정하려면 평가셋을 키워야 한다. 채택한 변경 중 답변 단계의 것
  (규칙 완화)은 유의성이 없는 상태로 남아 있다.
- **평가셋 출처**. 코퍼스에서 생성했으므로 실제 사용자 질문 분포와 다를 수 있다.
  실사용 질의 로그가 쌓이면 그것으로 교체하는 편이 낫다.
- **단일 문서군**. 현재 코퍼스는 GitLab DAP 관련 자료 하나다. 문서군이 늘면
  RRF 상수와 FINAL_K 를 재측정해야 한다.
- **LLM 오류 메시지**. API 크레딧 소진 시 사용자에게는 "응답 생성 중 오류가
  발생했습니다" 로만 표시된다. 운영자가 원인을 구분할 수 없다.

## 7. 운영 메모

- 배포는 `scripts/deploy.sh` 로만 한다. 문법 오류가 있는 파일을 커밋·배포한
  사고가 있었다. 이 스크립트는 `set -e` 로 어느 단계든 실패하면 중단하고,
  로컬 전체 컴파일 → S3 → EC2 압축 해제 후 재컴파일 → 재시작 → 헬스체크
  순으로 게이트를 건다.
- 아래 값은 환경변수로 덮어쓸 수 있다. 기본값은 위 실측에 근거한다.

| 환경변수 | 기본값 | 근거 |
|---|---|---|
| `RRF_K` | `10` | 3.1 (recall@5 p=0.012 유의) |
| `RETRIEVAL_FINAL_K` | `20` | 3.4 (K=7 대비 p=0.092 경향) |
| `CO_RETRIEVAL_MODE` | `off` | 3.3 (정확도 동률, 조회 비용 절감) |
| `RERANK_MODE` | `off` | 이 코퍼스에서 리랭커 변별력 없음 (`grader.py` 주석) |

답변 규칙(생성 프롬프트)은 `generator.py` 의 `_COMMON_PRINCIPLES` 에 있고,
변경 경위는 같은 파일 주석에 남겼다.

코퍼스 성격이 바뀌면 전부 재측정할 것.
